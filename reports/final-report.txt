Abstract
We implemented and evaluated a set of optimizations for the Expert Parallelism
(EP) layer inside Mixture-of-Experts (MoE) language models, focusing on two
bottlenecks: token scatter and the expert feed-forward network (FFN). For scatter,
we built five progressively improved CUDA kernels and integrated them into a
complete multi-GPU EP prefill and decode pipeline. For the FFN, we evaluated two
alternatives to the sequential per-expert cuBLAS approach: a blocksparse kernel
and a CUTLASS grouped GEMM. We benchmarked on NVIDIA Tesla V100-
SXM2-32GB GPUs at the Pittsburgh Supercomputing Center and on NVIDIA
A100-SXM4-40GB GPUs via Modal cloud. Our best scatter kernel reduces scatter
latency by 12.7x on V100 for T= 2048 tokens, producing a 1.22x end-to-end EP
round speedup. On A100, combining CSort scatter, communication overlap, and
CUTLASS grouped GEMM reduces 2-GPU Zipf prefill round time from 6.38 ms to
4.62 ms, a 1.38x speedup over the Atomic baseline. At fixed workload T= 8192 ,
the optimized 8-GPU pipeline reduces prefill time from 503.4 ms for the 1-GPU
Atomic baseline to 100.2 ms under uniform routing, a 5.03x end-to-end speedup.
Under Zipf routing, the same comparison reaches only 1.92x speedup, showing
that hot-expert imbalance is the main scaling bottleneck. Blocksparse FFN was
slower than packed cuBLAS in all configurations we tested. Pipeline overlap is
most useful in decode workloads, where it improves latency by 10–27%, but its
benefit in prefill depends on whether communication can be hidden behind enough
local computation.
1 Background
1.1 Mixture-of-Experts and Expert Parallelism
A Mixture-of-Experts (MoE) layer replaces a standard feed-forward network with a set of E expert
networks and a gating module that sends each token to a small subset of these experts at runtime [3].
With top-K routing, each token is assigned to K experts out of E, where typically K≪E . Only
the chosen experts run for that token, which keeps per-token compute roughly constant even as the
number of experts grows. When the model is small enough to fit on one GPU, all E experts live
on the same device and the layer is dominated by the FFN matrix multiplications. When the model
grows beyond single-GPU memory, Expert Parallelism (EP) splits the experts across N GPUs so
that each GPU holds E/N of them [2]. This shrinks per-GPU FFN cost roughly linearly in N, but it
also means that most tokens now live on a different GPU than their assigned expert. Before expert
computation can begin, tokens must be rearranged and packed into contiguous memory according to
their assigned experts. The cost of this movement does not shrink with N in the same way the FFN
does, so as N grows, token movement becomes the new bottleneck. Figure 1 shows the five stages
that a single MoE layer goes through under EP for a batch ofTtokens.
In stage 1 (scatter), each GPU reorders its local token embeddings by expert destination into a
contiguous packed buffer. In stage 2 (dispatch), each GPU sends each contiguous expert-block to the
GPU that owns that expert, using NCCL AllToAll. In stage 3 (FFN), each GPU runs a local FFN

using cuBLAS. In stage 4 (combine), the processed tokens are sent back to the GPU they originally
came from, again using NCCL AllToAll. In stage 5 (merge), each token’s K expert outputs are
combined using the gate weights produced during routing.

1.3 Workload Analysis
The scatter stage has three sources of parallelism as shown in Figure 1. The first isacross tokens.
The T K token-expert pairs are independent in the sense that the expert assignment for each token has
already been decided by the gate. The only dependency is on the per-expert counter that determines
packed-buffer position. The second source iswithin a row. Each row has d fp16 values, which
equals d/8 chunks of 16 bytes when read as uint4. A warp’s 32 lanes cooperate on this row, with
each lane handling d/256 chunks in a stride-32 loop. On one hand, each lane uses 16-byte (uint4)
loads and stores instead of 2-byte fp16 ones, which cuts the instruction count by a factor of 8. On the
other hand, in any single iteration of the loop the 32 lanes access 32 consecutive 16-byte chunks, so
the hardware merges their loads into wide HBM transactions and merges their stores in the same way.
The only requirement is that d be a multiple of 8 so the row aligns to uint4 boundaries; this holds
for all model sizes we test, where d= 2048 matches Qwen1.5-MoE-A2.7B and gives 256 chunks per
row, 8 chunks per lane. The combination of vectorization and coalescing brings scatter close to the
bandwidth ceiling for a pure copy. The third source is at thewarp level. Computing the destination
slot s for each row requires an atomic increment on expert_count[e], because multiple warps
processing different tokens may target the same expert region. In the per-thread design, each lane
handles its own token and does its own atomic, so a warp issues 32 atomics. In this project, one warp
is dedicated to one (token, expert) pair: lane 0 alone performs the atomic, and the resulting slot index
is broadcast to the other 31 lanes through a warp shuffle. The other lanes then participate in copying
the row.
Locality is good for reads and writes individually but poor across rows. Reading row t from
embeddings is a contiguous d-element load. Writing row t to packed is a contiguous d-element
store. But two adjacent threads handling two adjacent tokens may write to two completely different
regions of packed because their tokens went to different experts. The access pattern within a row is
dense and regular, but the mapping from input rows to output rows is data-dependent.
The FFN stage, by contrast, has no such irregularity once the data is packed. Each per-expert sub-
buffer is a dense [ne, d]×[d, d ffn] matrix multiplication, which maps cleanly onto Tensor Cores. The
challenge in the FFN is different. With E= 64 experts on one GPU, the standard approach issues 64
separate cuBLAS calls, one per expert. Each call has fixed launch overhead. Under skewed routing,
many experts receive only a handful of tokens, and the per-call overhead dominates the actual matmul
time. A grouped GEMM kernel that handles all 64 experts in one launch can recover this overhead.

2 Approach
2.1 Technologies and Target Platforms
We implemented all kernels in CUDA C++. We used CUB for the radix sort and exclusive prefix
sum primitives in the sort-based scatter kernels, CUTLASS for the grouped GEMM, and NCCL for
inter-GPU point-to-point send/recv and AllGather.
We targeted two GPU platforms. The first is NVIDIA Tesla V100-SXM2-32GB at PSC Bridges-2,
running CUDA 12.6.1 with CUB and NCCL. The second is NVIDIA A100-SXM4-40GB through
Modal cloud, running CUDA 12.4.1 with CUTLASS 3.5.1 and NCCL. The two platforms exercise
different parts of the design space. V100 is more strictly bandwidth-bound, so memory-movement
optimizations show up clearly in scatter latency. A100 has more compute headroom and faster
Tensor Cores, which makes the FFN launch overhead more visible and motivates the grouped GEMM
experiments.
2.2 Atomic Baseline
The baseline pipeline runs a count kernel that builds a shared-memory histogram of expert assign-
ments and flushes it to a global expert_count array, then a CUB exclusive prefix sum to produce
expert_start, and finally a scatter kernel where each thread handles one (token, expert) pair
independently. This design has two performance bottlenecks.First, every thread calls atomicAdd
on the same per-expert counter, so threads assigned to the same hot expert must serialize. Under Zipf
distribution this is severe.Second, the element-by-element copy loop is not vectorized, and the 32
threads in a warp write to 32 different row addresses, so the GPU cannot merge their stores into a
single wide memory transaction.
2.3 Scatter Optimization
We built four improved kernels on top of the atomic baseline. Figure 4 shows how each kernel maps
the work onto GPU execution units: the unit of work is one row of the packed buffer, which is
assigned to either a thread block (Sort) or a single warp of 32 lanes (Warp, Vec, CSort), with lane
i handling chunks i, i+ 32, i+ 64, . . . of the row in a stride-32 loop. The figure also shows which
rows each unit writes and how it handles the per-expert counter.
Sort.The sort strategy replaces the scatter kernel with a CUB radix sort on expert IDs (using only
⌈log2 E⌉ bits), followed by a gather kernel that assigns one 256-thread block to each output row.
Because the sort pre-determines every slot’s destination, there are no atomics in the gather phase. All
256 threads in a block write consecutive elements of the same output row, so their stores coalesce
into 128-byte transactions. The trade-off is two extra HBM passes for the sort’s temporary key and
value arrays.
4
PAGE 5
Figure 4: Five CUDA kernel strategies for packing rows into a contiguous buffer.
Warp.The warp strategy keeps the same sort pipeline but changes only the gather kernel geometry.
Instead of one block per row, it assigns one warp (32 lanes) per row, with four warps sharing a
single block launch. This produces four times fewer block launches than Sort, reducing launch
overhead. The stride-32 access pattern remains coalesced because all 32 lanes in a warp read and
write consecutive elements within one warp step.
Vec.The vec strategy is identical to Warp but reinterprets the fp16 embedding array as uint4 (16
bytes, holding 8 fp16 values) so that each load/store instruction moves 16 bytes instead of 2. This
reduces the number of load and store instructions per row by a factor of 8, freeing SM issue slots. It
also fuses the two-kernel bounds-plus-count sequence into a single kernel, saving one kernel launch.
The requirement is thatd_modelis a multiple of 8.
CSort.CSort avoids the radix sort entirely, eliminating its two extra HBM passes. It reuses
the same count kernel and prefix sum as the baseline to build expert_start, then runs a single
place_gather kernel where lane 0 of each warp performs the atomic and broadcasts the result. The
key difference from the atomic baseline is that the atomic runs once per warp rather than once per
thread, cutting atomic operations by a factor of 32. For the hottest expert under Zipf, this means
roughly 50 sequential atomic operations instead of over 1000. The __shfl_sync call broadcasts the
slot position to all 32 lanes using warp registers with no global memory access. All lanes then copy
the embedding row with the same vectorizeduint4pattern as Vec.
Iteration.The four kernels were developed in the order presented, each step driven by the previous
one’s bottleneck. Atomic serializes threads that share the same expert counter, every thread issues
its own atomicAdd, and the hardware queues them at the L2 cache. Sort makes the gather phase
lock-free by fixing every slot’s destination ahead of time, but launches one block per row. Warp
shrinks the per-row unit to a single warp, cutting block launches by 4x. Vec then widens each lane’s
memory instructions from 2-byte fp16 to 16-byte uint4, reducing instruction count by 8x. At this
point the radix sort’s two extra HBM passes became the bottleneck, so CSort drops the sort, keeps the
warp-per-row uint4 copy from Vec, and reserves slots through a single per-warp atomic broadcast
via__shfl_sync.
2.4 FFN Optimizations
Each expert’s FFN follows the standard two-layer design used in Transformer feed-forward blocks [1],
with two weight matricesW 1 ∈R d×dffn andW 2 ∈R dffn×d separated by a nonlinearity:
F F Ne(x) =W 2 ·σ(W 1 ·x),(1)
where σ is a pointwise activation. We refer to the W1 step as the up-projection (mapping d→d ffn)
and the W2 step as the down-projection (mapping dffn →d ). In our experiments d= 2048 and
dffn = 8192, matching Qwen1.5-MoE-A2.7B.
The packed FFN baseline issues one cuBLAS HGEMM call per expert for each of the two matmuls,
giving 2E= 128 sequential calls per FFN pass with E= 64 . The launch overhead of these calls
dominates the compute time when expert groups are small. Both alternatives we explored target
the up-projection, since it is the more memory-traffic-intensive of the two matmuls and the one that

benefits most from fused-gather techniques. Figure 5 compares the three implementations of the
up-projection.
Blocksparse.The blocksparse approach fuses the scatter step and the up-projection into a single
kernel, following the Megablocks design [ 1]. Instead of materializing the packed buffer before
W1, the kernel reads token rows directly from the original embeddings through the sorted index
produced during routing, and computes embeddings[perm]·W 1 in place. This saves one full HBM
read-and-write of the packed buffer.
Grouped GEMM.We replaced the E sequential cuBLAS calls for W1 with a single CUTLASS
GemmGrouped kernel that handles all expert up-projections in one launch. The kernel takes a list
of per-expert pointer-and-shape tuples, and the GroupedGEMM scheduler runs the E matmuls
concurrently on different SMs inside one launch. Tensor Cores are used at full throughput, since each
per-expert input slice is contiguous in the packed buffer.
2.5 Origin of Code
All kernels were written from scratch. We studied the open-source implementations of ScatterMoE [4],
MegaBlocks [1], DeepEP [ 5], and SGLang/vLLM as design references for scatter and dispatch
patterns.
3 Results
3.1 Experimental Setup
All results are medians over multiple repeated runs after warmup, averaged across participating GPUs.
Model dimensions match Qwen1.5-MoE-A2.7B: E= 64 , K= 4 , dmodel = 2048, dffn = 8192. We
used two expert assignment distributions. Uniform assigns tokens with near-equal load across experts.
Zipf generates roughly 9–11x load imbalance, modeling skewed real-world inference traffic.
We evaluated 2-GPU, 4-GPU, and 8-GPU EP configurations using NCCL point-to-point send and
recv for the dispatch and combine stages, with an AllGather before each dispatch to collect per-
expert token counts so every GPU knows how many tokens to expect from each peer. Within each
configuration we tested two scheduling modes. In serial mode each pipeline stage runs to completion
before the next begins. In overlap mode, scatter and FFN run on one CUDA stream while NCCL
AllToAll runs on a second stream, with event-based synchronization between them.

3.8 Analysis
Several patterns summarize the results across all experiments.
Scatter optimization is necessary but not sufficient.Reducing scatter from 1.28 ms to 0.10 ms is a
12.7x improvement, but it only produces a 1.22x end-to-end speedup on V100 because FFN dominates.
Under Zipf on A100, CSort with cuBLAS FFN gives only a modest 1.15× improvement over the
Atomic baseline because the FFN time is amplified by load-imbalanced cuBLAS sequential calls;
switching to grouped GEMM is required to translate scatter savings into a meaningful end-to-end
speedup. The grouped GEMM is needed to realize the full benefit.

Grouped GEMM wins under Zipf.Sequential cuBLAS makes 64 separate GEMM calls, each
with fixed launch overhead regardless of expert group size. Under Zipf, many experts are tiny and
launch overhead dominates. A single grouped GEMM kernel handles all 64 experts together and
is 1.22x faster than sequential cuBLAS under Zipf. Under uniform assignment the gain is smaller
(1.07–1.13x) because all expert groups are roughly equal-sized and cuBLAS is well-utilized.
Blocksparse FFN is not practical.The blocksparse kernel is up to 31x slower than packed cuBLAS
at T= 2048 Zipf. Avoiding the scatter step does not compensate for the FFN throughput loss. The
irregular access pattern prevents the Tensor Cores from reaching high utilization.
Pipeline overlap works at decode scale, not prefill scale.In large prefill batches (V100,T≥256 , 2–
4 GPUs), overlap made performance 3–6% worse. In decode mode (A100,T≤256 , 4 GPUs), overlap
saved up to 27%. The difference is that decode rounds are short enough that the communication time
is a meaningful fraction of total time, so hiding it behind computation helps. In long prefill rounds,
the fixed CPU sync cost dominates and erases the benefit.
Scaling to more GPUs makes EP overhead more important.At 4 GPUs, each GPU’s FFN is
half the size of the 2-GPU case, but scatter and communication do not shrink proportionally. EP
overhead at 4 GPUs with Atomic baseline reaches 27% of round time. This means the combined
scatter-plus-grouped-GEMM optimization becomes more impactful at higher EP degree.
4 Conclusion
This project shows that optimizing MoE expert parallelism requires addressing both irregular token
movement and expert computation. Scatter alone is highly optimizable: replacing the Atomic baseline
with CSort reduces scatter latency by 12.7x on V100 by reducing atomic contention, improving
memory coalescing, and avoiding unnecessary HBM passes. However, the end-to-end gain from
scatter alone is limited because the FFN remains the dominant stage.
On A100, the FFN bottleneck becomes especially visible under skewed routing, where many experts
receive small token groups and sequential per-expert cuBLAS calls underutilize the GPU. CUTLASS
grouped GEMM reduces this overhead by executing many expert matmuls in a single kernel launch.
Combined with CSort and overlap, grouped GEMM produces the best end-to-end prefill result.
The strong-scaling experiment shows that the optimized EP pipeline gives real multi-GPU acceleration,
not only weak-scaling throughput growth. At fixed T= 8192 , the optimized 8-GPU pipeline is
5.03x faster than the 1-GPU Atomic baseline under uniform routing. The same experiment reaches
only 1.92x under Zipf routing, which identifies load imbalance as the main remaining bottleneck. In
future work, this suggests that routing-aware load balancing, expert replication, or dynamic expert
placement may be needed in addition to faster scatter and FFN kernels.
